# MPS Flexi product reference page rewrite

A complete rebuild of the MPS Flexi insurance product HTML page from a ~625-line skeleton into a ~1210-line self-contained reference tool. The page now has 10 tabs covering product summaries, per-plan detail, premium tables, an interpolation-based calculator, password-gated commission data, training material, and FAQ. Designed as a mobile-first sales tool for Indonesian insurance agents to share with prospective customers via WhatsApp.

**Watch for:** Client-side password protection on the Commission tab offers zero actual security (confirmed). The calculator's linear interpolation between sparse data points produces premium estimates that may diverge from actual Manulife rate cards for non-anchor ages (confirmed). The base64-embedded commission image adds ~375KB to every page load with no lazy-loading (confirmed).

## High-level view

The page serves as both a customer-facing product explainer and an agent-facing sales tool, with the commission tab as the only differentiation between the two audiences. The password mechanism (`if (pwd === '123')`) is a visibility toggle, not access control; anyone who views source or inspects the DOM can read the commission data immediately.

The calculator implements linear interpolation over known premium data points. For ages on anchor points (18, 20, 25, 30, 35, 40, 45, 50, 55, 60), results are exact. For intermediate ages, the linear approximation introduces error that grows at older ages where mortality curves are exponential. The "estimasi" disclaimer is present but the divergence from actual rate cards is unquantified.

The self-contained single-file design (no external dependencies) makes it reliable for offline/WhatsApp sharing but the inline base64 commission image (~375KB) forces every visitor to download agent-only content, adding ~8 seconds on 3G connections. The tab bar with 10 items requires significant horizontal scrolling on mobile, and the sticky banner/tab stack will overlap if banner text wraps on very narrow screens (<320px).

<summary>Issues (5)</summary>

1. **Commission password is client-side plaintext** — The password "123" is visible in page source. Anyone can read it, or simply toggle `.komisi-content` visibility via DevTools. If commission data is genuinely sensitive, move it behind a server-side gate or accept this as a casual deterrent only.
2. **Interpolation gaps for non-anchor ages** — Plan A has no data point between ages 20 and 25, or 25 and 30 (5-year gaps). Ages like 21, 23, 24 are purely interpolated guesses that may not match official Manulife rates. Actual mortality curves are exponential, not linear.
3. **375KB base64 image blocks initial render** — The commission JPEG is inline in the HTML body. On slow mobile connections this will delay first meaningful paint for the entire page, not just the commission tab.
4. **No ARIA roles or keyboard navigation on tabs and FAQ** — The tab bar uses `<li onclick>` with no `role="tab"`, `aria-selected`, or keyboard event handling. FAQ items use `onclick` on a `<div>` with no `role="button"` or keyboard support. Screen readers and keyboard-only users cannot interact.
5. **Monthly figure divides annual by 12 but product only supports annual payment** — Showing "per bulan" figures could mislead customers into thinking monthly payment is available. The FAQ clarifies annual-only, but the calculator result is more prominent.

## Commission tab password as visibility toggle

The `checkKomisiPassword()` function compares user input against the string `"123"` in plaintext JavaScript:

```javascript
if (pwd === '123') {
  document.getElementById('komisi-lock').style.display = 'none';
  document.getElementById('komisi-content').style.display = 'block';
}
```

The commission content (tables and the base64 image) is present in the DOM on page load, hidden only by `display:none`. Any user who opens browser DevTools can see the content immediately. The risk: someone shares this page with customers not realizing the commission data is trivially accessible to anyone.

## Calculator interpolation accuracy

For non-anchor ages, `interpolateRate()` performs simple linear interpolation:

```javascript
var ratio = (age - ages[i]) / (ages[i + 1] - ages[i]);
return rates[i] + ratio * (rates[i + 1] - rates[i]);
```

Actual mortality tables are exponential, not linear. The error grows as the gap between anchor points widens and at older ages where mortality curves are steeper. Plan A has anchor points at ages 18-19-20 (1-year gaps) then jumps to 25 (5-year gap). Ages 21-24 are interpolated across this 5-year gap, and ages 51-54 are interpolated between 50 and 55 where the rate jumps from 740,000 to 1,000,000 (35% increase). The linear approximation will underestimate premiums in the upper part of each interval.

The Tabel Premi tab does show some intermediate ages (22, 28, 32, 38, 42, 48, 52, 58) with values that match the interpolation, suggesting the table itself was generated from the same linear model rather than from official Manulife rate cards. If the official rates follow a different curve, both the table and calculator are wrong together.

## Base64 image payload

The commission JPEG is inline as `data:image/jpeg;base64,...` (~375KB of base64 text, ~280KB decoded). Since this is inline HTML, browsers must download and parse the entire string before rendering any part of the page. The image is only relevant to agents who unlock the commission tab, but loads for every visitor.

A practical mitigation without breaking the single-file constraint: store the base64 string in a JavaScript variable and inject it as the `src` only after password entry. This wouldn't reduce download size but would allow the browser to begin rendering the page before parsing the image data.

## Tab and FAQ accessibility gaps

The tab bar is built with `<ul><li onclick="showTab(N)">` elements. No `role="tablist"` / `role="tab"` / `aria-selected` attributes, no `tabindex` management, no keyboard event handlers for arrow-key navigation. A keyboard-only user must Tab through all 10 items sequentially.

FAQ items use `<div class="faq-item" onclick="this.classList.toggle('open')">`. Not focusable (no `tabindex`), no `role="button"`, no Enter/Space handlers. Screen readers will not announce them as interactive elements.

## Monthly estimate misleads on payment frequency

The calculator shows both annual and monthly figures:

```javascript
document.getElementById('calc-monthly').textContent = '(setara ' + monthlyStr + ' / bulan)';
```

The FAQ clarifies payment is annual-only, but the calculator result showing "Rp 333.000 / bulan" prominently could set customer expectations that monthly payment is supported. Consider adding "(pembayaran tahunan)" next to the monthly estimate, or removing it entirely.

## Sticky header overlap on narrow screens

The sticky positioning stack assumes the banner height is exactly 48px (`top:0` for banner, `top:48px` for tabs). The banner has `padding:12px 15px` with a single line of text. If the banner text wraps on screens narrower than ~320px, the banner becomes taller than 48px and the tab bar will be hidden underneath it.

## "Biaya Bersih Proteksi: Rp 0" claim

The comparison table states "Biaya Bersih Proteksi: Rp 0 (kembali semua)" for Plans B and C. This is nominally true but economically misleading - it ignores the time value of money over 15 years. A customer investing Rp 330 million over 15 years at even a modest 5% return would accumulate significantly more. The highlight box below mentions "opportunity cost" but the bold "Rp 0" in the table is what customers will remember. Consider rephrasing to "Rp 0 (nominal)" or adding a footnote about opportunity cost directly in the table row.
