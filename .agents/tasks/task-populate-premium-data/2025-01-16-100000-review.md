# Data-driven premium lookup for MPS Flexi calculator

The hardcoded `getBaseRate()` function (7 sample entries returning a dummy 10M rate for all unknown combos) is replaced with a 1523-entry lookup table extracted from `Data_Premi_MPS_Clean.json`. A Python script (`extract_premi_data.py`) parses 135 seventeen-row blocks, determines age/gender/currency from positional conventions in the data, and writes the result as a `const dataPremiJSON` array directly into the HTML. The `calculate()` function now gracefully handles missing data by showing "DATA BELUM ADA" instead of computing with a dummy rate.

**Watch for:** Ages 31-64 are entirely absent from the extracted data (confirmed) — the calculator will show "DATA BELUM ADA" for the most common working-age customers. Floating-point rounding produces off-by-one IDR values like 130,699,999 instead of 130,700,000 for 8 entries (confirmed). The 121 KB inline JSON array quadruples the HTML file size with no lazy-loading path (confirmed).

## High-level view

The extraction script handles 135 blocks of varying shapes (4-block normal, 3-block special for ages 7 and 15, 2-block for ages 65-70, 1-block for age 39) through a positional heuristic for gender assignment. The heuristic is hardcoded per block count and currency pattern — if the source data ever changes ordering, gender assignments silently break without validation.

The embedded data covers ages 0-30, 39, and 65-70 (38 distinct ages), but not 31-38 or 40-64. This is a data-source limitation, not a code bug, but the calculator's UI allows selecting any age 0-70, so the majority of adult users will hit the "DATA BELUM ADA" fallback. Plan A (Amanah) has only 38 entries because most young-age YRT cells in the source contain "-".

Inlining 121 KB of JSON in a single HTML file is pragmatic for a zero-infrastructure calculator but grows the page from 37 KB to 161 KB. The premium data, the extraction script, and the presentation layer are tightly coupled — any data update requires re-running the Python script and committing the entire HTML file.

## Incomplete age coverage

The source file `Data_Premi_MPS_Clean.json` contains only 135 blocks covering ages 0-30, 39, and 65-70. Ages 31-38 and 40-64 have no data in this file at all. The calculator is functionally broken for adult customers between 31 and 64 (excluding age 39) — which represents most of the target market for life insurance products. The data gap originates from the source PDF not yet being digitized for those ages.

## Gender assignment heuristic for irregular blocks

The script groups blocks by age and assigns gender based on block count and currency pattern:

```
4 blocks (standard): [IDR_Pria, USD_Pria, IDR_Wanita, USD_Wanita]
3 blocks: pattern-match currency list against known anomalies
2 blocks: [Pria, Wanita]
1 block:  [Pria]
```

For age 7 (3 blocks: IDR, IDR, USD), the script assigns IDR-Pria, IDR-Wanita, USD-Wanita — meaning Pria USD data for age 7 is absent from the output. For age 15 (3 blocks: IDR, USD, USD), it assigns IDR-Pria, USD-Pria, USD-Wanita — meaning Wanita IDR data for age 15 is absent. These are silent gaps: the extraction script doesn't log or warn about missing gender-currency combinations. A user selecting Pria/USD/age 7 gets "DATA BELUM ADA" even though data may exist elsewhere in the source.

## Floating-point truncation in IDR conversion

The `parse_rate` function converts IDR values via `int(float(value) * 1_000_000)`. Because IEEE 754 cannot represent some decimal values exactly, `130.7 * 1_000_000` evaluates to `130699999.99...` which truncates to `130699999`. This affects 8 entries. Using `round()` instead of `int()` would eliminate the issue:

```python
return round(float(value) * 1_000_000)
```

The error is 1 Rupiah on premiums in the hundreds-of-millions range — negligible for calculations but visually wrong to anyone spot-checking against the source table.

## Lookup performance

`getBaseRate` performs a linear scan via `Array.prototype.find()` over 1523 objects, matching on 6 fields. At current data size this completes in sub-millisecond time per button click. A lookup map would be both faster and would make it trivial to enumerate missing combinations at startup:

```javascript
const premiumMap = {};
dataPremiJSON.forEach(d => {
    premiumMap[`${d.plan}|${d.gender}|${d.age}|${d.mb}|${d.ml}|${d.curr}`] = d.rate;
});
```
