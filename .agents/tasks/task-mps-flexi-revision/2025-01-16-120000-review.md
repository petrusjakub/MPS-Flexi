# Multi-term calculator and product spec revision for MPS Flexi

The single-file product page was revised to support multiple payment terms (masa bayar) per plan: Plan A now offers 1/5/10-year terms, Plan B offers 5/10/15 years, and Plan C offers 5/10/15 years. The calculator was restructured around a `terms` object per plan with dynamic dropdown population, and the UP input changed from a fixed `<select>` to a hybrid text + datalist allowing free-form entry. A live USD exchange rate is fetched from a public API with a 16,500 IDR fallback. Product spec text across all ten tabs was updated to reflect the new term structures, expanded age limits (Plan A now 17-70), and corrected masa perlindungan rules (Plan B covers to age 110, Plan C coverage is 15 or 25 years depending on payment term).

**Watch for:** The Plan B premium table claims to show 15-year term rates but actually displays the 5-year term data from the JS object (confirmed). The calculator says "kontribusi tetap selama X tahun" for Plan A regardless of term, which is misleading for the 1-year YRT option where premiums renew and increase annually (confirmed). The UP input's `formatUPInput()` fires on every keystroke via `oninput`, stripping and reformatting mid-typing, which can jump the cursor position and frustrate mobile users (likely).

## High-level view

The premium data restructuring is the core engineering change: the flat `ages`/`rates` arrays were replaced with a `terms` map keyed by payment duration, each containing its own `ages` and `rates`. This cleanly supports the per-plan dropdown population and interpolation lookup without conditional branching. However, the Plan B premium table in the Tabel Premi tab is now inconsistent with the JS data - it says "masa bayar 15 tahun" in its header but the numbers match the `terms['5']` key (530,000 for age 17), not `terms['15']` (290,000).

The exchange rate fetch from `open.er-api.com` fires immediately on script load as an IIFE, with a graceful fallback to 16,500 IDR. The `updateKursDisplay()` function keeps the currency selector label and info text synchronized. There is no `AbortController` timeout on the fetch, so on degraded networks the promise could hang before the catch path fires.

The hybrid UP input (text + datalist) allows any value >= 100 million but the aggressive `oninput` reformatting will repeatedly reformat the field as the user types, jumping cursor position. The minimum enforcement is silent - `getUPValue()` returns 100M without user feedback if below threshold.

## Plan B premium data mismatch between table and calculator

The HTML premium table for Plan B contains a header that reads "Tabel di bawah untuk masa bayar 15 tahun" and displays rates starting at Rp 530.000 for a 17-year-old male. In the restructured `premiumData.B.terms` object:

```javascript
'5':  { ages: [17,...], rates: [530000,...] },   // matches the table
'15': { ages: [17,...], rates: [290000,...] }     // does NOT match the table
```

The 530,000 figure matches the `'5'` key. The economic logic confirms this - shorter payment terms require higher annual premiums. The table numbers track the 5-year term, not the 15-year term as claimed.

The comparison table compounds this by stating "Rp 22 juta/tahun (Pria 40th, UP 1M)" for Plan B. That figure is `terms['5']` age 40 (2,200,000) multiplied by 10, confirming the page's example pricing references the 5-year term. But the "Total Bayar" column says "Rp 330 juta (15th)" implying 22M x 15 years, which would only make sense if the 15-year rate were 22M/year - but with the actual `'15'` term data, a 40-year-old male at UP 1M would pay approximately 12.4M/year x 15 = 186M total.

This is a product accuracy issue that could mislead agents and customers.

## Plan A calculator messaging for YRT vs multi-year terms

When Plan A is selected with masa bayar "1" (the YRT option), the calculator produces:

```
Plan A: kontribusi tetap selama 1 tahun. Tidak ada pengembalian.
```

The phrasing "kontribusi tetap" echoes the messaging used for Plans B and C where premiums genuinely stay flat across the full payment period. For the 1-year YRT, each annual renewal brings a new (higher) rate. A user who sees "tetap selama 1 tahun" and renews for 20 years may not understand that next year's renewal will cost more.

For the 5-year and 10-year Plan A terms, the rates in the JS data (`terms['5']` and `terms['10']`) are distinct from the 1-year rates but there's no product documentation clarifying whether these represent locked rates for the full term or averaged/initial rates.

## Hybrid UP input cursor behavior

The `<input type="text" id="calc-up-input" ... oninput="formatUPInput()">` fires on every character:

```javascript
function formatUPInput() {
  var input = document.getElementById('calc-up-input');
  var val = input.value.replace(/[^0-9]/g, '');
  var num = parseInt(val);
  if (!isNaN(num) && num > 0) {
    input.value = num.toLocaleString('id-ID');
  }
  calculate();
}
```

Each invocation strips dots, parses, then reformats with dots. The cursor position is not preserved, jumping to end each time. On mobile keyboards where the input is `type="text"`, the numeric keyboard won't appear automatically. Debouncing to `onblur`/`onchange` and adding `inputmode="numeric"` would address both issues.
